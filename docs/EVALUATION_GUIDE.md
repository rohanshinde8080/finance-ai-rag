## 1. Quick Start Demonstration Setup

### Option A: Local Development Mode (Recommended for Fast Viva Setup)
1. Ensure PostgreSQL is running locally on port `5432` with a database named `finance_ai_db`.
2. Double-click **`run_dev.bat`** (or execute `./run_dev.bat` in Command Prompt / Terminal).
3. The launcher will automatically:
   - Start the FastAPI Backend on `http://localhost:8000` (auto-runs migrations and admin seeding).
   - Start the Vite React Frontend on `http://localhost:5173`.
4. Open your browser to:
   - **User Application:** `http://localhost:5173`
   - **Admin Portal:** `http://localhost:5173/admin/login`
   - **Interactive API Documentation:** `http://localhost:8000/docs`

### Scenario 3: Financial PDF Ingestion & Real-Time Vectorization
1. Click **"Documents & RAG"** in the Admin sidebar (`/admin/documents`).
2. Upload a sample financial circular or notice:
   - **Title:** "Master Circular on Customer Service in Banks"
   - **Category:** Banking & RBI Guidelines
   - **File:** Select any PDF document (magic-byte `%PDF-` verified).
3. Click **"Ingest & Vectorize"**.
4. Show the evaluator the live processing pipeline:
   - PyMuPDF extracts text page-by-page.
   - Text cleaner removes headers, form feeds, and redundant whitespace.
   - Recursive chunker splits text into ~800-character overlapping chunks.
   - `SentenceTransformer('all-MiniLM-L6-v2')` computes 384-dimensional dense vectors.
   - Embeddings are written to PostgreSQL `document_chunks` table via `pgvector` AND added to the in-memory FAISS `IndexIDMap2`.
   - Document status transitions immediately to `INDEXED`.

### Scenario 5: Dynamic Regulatory Fallback (Unindexed Query)

   - Maximum similarity score from vector search is below threshold ($\tau < 0.70$).

## 4. Key Examiner Questions & Technical Defenses

### Q1: Why did you eliminate SQLAlchemy and Alembic in favor of direct `psycopg`?
> **Defense:** Financial and regulatory systems require deterministic, high-throughput database interactions. ORMs introduce hidden query latency (N+1 queries), object transformation overhead, and complex state management. Using `psycopg` v3 directly with `psycopg_pool.ConnectionPool`:
> - Grants sub-millisecond execution control.
> - Allows native registration of the `pgvector` adapter (`register_vector`) for direct binary serialization of float vectors.
> - Relies on clear, auditable SQL scripts for schema migrations without ORM abstraction drift.
> - Enforces parameterized SQL queries `%s` for 100% protection against SQL injection.

### Q2: Why maintain dual vector stores (PostgreSQL `pgvector` AND FAISS)?
> **Defense:** They serve two complementary architectural purposes:
> 1. **Durable Persistence (PostgreSQL `pgvector`):** Vector embeddings must survive application restarts, support relational integrity (foreign keys to `documents`), and adhere to ACID database backups.
> 2. **Ultra-Low Latency Retrieval (FAISS):** Searching dense vectors in disk-bound SQL tables under concurrent user load can suffer from I/O bottlenecks. FAISS holds normalized L2 vectors in RAM using `IndexIDMap2(IndexFlatIP)`, performing cosine similarity in sub-5 milliseconds. The backend automatically warms FAISS from PostgreSQL on cold boot.

### Q3: How does FinanceAI prevent hallucination?
> **Defense:** Hallucination prevention is enforced through three mechanisms:
> 1. **Low Temperature Inference:** Gemini API is configured with temperature $0.2$ to minimize speculative generation.
> 2. **Strict Grounding Prompts:** Gemini is explicitly instructed to refuse to answer if the context does not contain sufficient factual evidence, and is prohibited from fabricating sources.
> 3. **Quantitative Similarity Gate:** If retrieval similarity is below $0.70$, the query is never forced into document generation; it transitions safely to official regulatory web search.
